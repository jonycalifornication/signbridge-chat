# signBridge-avatar
-----

# ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ)

**Название проекта:** Web-виджет 3D-сурдопереводчика (Text-to-Sign Avatar)
**Целевая нагрузка:** 1000 одновременных пользователей.

## 1\. Общее описание

Сервис представляет собой встраиваемый JavaScript-виджет, который отображает 3D-аватара в углу веб-страницы. Виджет принимает текстовый ввод (от сайта или пользователя), отправляет его на сервер, получает последовательность жестов и воспроизводит их с помощью аватара.

**Ключевая особенность:** Гибридная архитектура. «Тяжелая» логика (NLP, подбор жестов) — на сервере. Рендеринг и анимация — на клиенте (браузер пользователя).

-----

## 2\. Архитектура системы

Система состоит из трех компонентов:

### 2.1. Client Side (Виджет)

  * **Технологии:** HTML5, CSS, Vanilla JS + **Three.js** + **@pixiv/three-vrm**.
  * **Роль:**
      * Отрисовка прозрачного Canvas поверх сайта.
      * Загрузка базовой модели аватара (VRM).
      * Получение JSON-плейлиста от сервера.
      * Загрузка мелких файлов анимаций (.glb/.vrma) по требованию.
      * **Blending (Смешивание):** Плавное склеивание анимаций, чтобы переходы между жестами были бесшовными.

### 2.2. Server Side (Backend API)

  * **Технологии:** Python (FastAPI) или Node.js (NestJS).
  * **Роль:**
      * Прием текста.
      * **NLP Engine:** Лемматизация текста, перевод в глоссы (Text-to-Gloss).
      * **Mapping:** Поиск соответствующих файлов анимации в базе данных для каждого глосса.
      * Формирование JSON-ответа (сценарий воспроизведения).

### 2.3. Storage & CDN (Хранилище)

  * **Технологии:** S3 (AWS/MinIO/Yandex Cloud) + CDN (Cloudflare/Nginx).
  * **Роль:** Хранение и быстрая отдача статических файлов: модели аватара и тысяч файлов анимаций.
  * *Важно для нагрузки:* 1000 пользователей не должны качать файлы с вашего API-сервера. Они должны качать их с CDN.

-----

## 3\. Функциональные требования

### 3.1. Виджет (Frontend)

1.  **Изоляция:** Скрипт не должен конфликтовать с CSS/JS родительского сайта. Использование Shadow DOM (желательно).
2.  **Легковесность:**
      * Начальный вес скрипта загрузчика \< 50 Кб.
      * Lazy Loading: Аватар загружается только после инициализации или первого взаимодействия.
3.  **Управление анимацией:**
      * Реализация очереди (`AnimationQueue`).
      * Поддержка `crossFade` (плавное перетекание из жеста А в жест Б за 0.2–0.3 сек).
      * Возврат в состояние Idle (ожидание) после окончания фразы.
4.  **Оптимизация производительности:**
      * Ограничение FPS до 30.
      * Автоматическая пауза рендера, если вкладка не активна.

### 3.2. Бэкенд (Backend)

1.  **API Endpoint:** `POST /api/v1/translate`
      * Вход: `{ "text": "Привет, как дела?", "avatar_id": "default" }`
      * Выход:
        ```json
        {
          "sequence": [
            { "url": "cdn.com/anims/hello.glb", "duration": 1.5, "face": "Joy" },
            { "url": "cdn.com/anims/how_are_you.glb", "duration": 2.0, "face": "Neutral" }
          ]
        }
        ```
2.  **Кэширование (Redis):** Обязательно кэшировать ответы NLP. Если 100 человек спросили одно и то же, сервер не должен запускать NLP-модель 100 раз.

### 3.3. База Данных Анимаций

1.  Таблица соответствий: `Слово/Глосс` -\> `ID файла анимации`.
2.  Хранение метаданных: Длительность анимации, требуемая эмоция на лице.

-----

## 4\. Требования к нагрузке (1000 пользователей)

Расчет ресурсов для 1000 одновременных пользователей:

### 4.1. Пропускная способность (Bandwidth)

  * Вес одной анимации (оптимизированный .glb): \~50–100 Кб.
  * Фраза из 5 слов: \~500 Кб.
  * 1000 пользователей одновременно получают фразу: 500 Мб трафика в моменте.
  * **Решение:** Использование **CDN** обязательно. Бэкенд отдает только ссылки (текст), файлы отдаются через распределенную сеть.

### 4.2. База данных и API

  * NLP обработка текста занимает время (10–50 мс).
  * 1000 запросов в секунду (RPS) — это нагрузка выше средней.
  * **Решение:**
      * Запуск нескольких воркеров (Gunicorn/Uvicorn).
      * Горизонтальное масштабирование (если нагрузка вырастет, просто добавляем еще один сервер с API).

-----

## 5\. Требования к контенту (3D Assets)

Для того чтобы система работала быстро и корректно:

1.  **Модель аватара (.vrm):**
      * Полигонаж: \< 15,000 треугольников.
      * Текстуры: 1 атлас 1024x1024 или 2048x2048.
      * Вес файла: Строго до 3-4 Мб.
2.  **Анимации (.glb/.vrma):**
      * **Stripping:** Удалены кости ног и таза (если виджет поясной). Оставлены только торс, руки, пальцы, шея, голова.
      * **FPS анимации:** 30 кадров/сек (снижает вес файла в 2 раза по сравнению с 60).
      * **Компрессия:** Использование Draco compression (опционально, если Three.js распакует быстро).

-----

## 6\. Этапы разработки (Roadmap)

### Этап 1: MVP (Прототип)

1.  Статичный HTML с виджетом Three.js.
2.  Хардкод на сервере: база из 50 популярных фраз/слов.
3.  Реализация плавного склеивания двух анимаций на клиенте.

### Этап 2: Интеграция NLP

1.  Подключение NLP-движка (стемминг/лемматизация).
2.  Наполнение базы анимаций (маппинг слов на файлы).
3.  API возвращает реальные цепочки жестов.

### Этап 3: Оптимизация под High Load

1.  Перенос файлов на S3 + Cloudflare.
2.  Настройка кэширования в Redis.
3.  Минификация JS-кода виджета.

-----

## 7\. Примерный стек для реализации

  * **Frontend:** JavaScript (ES6+), Three.js r160+, @pixiv/three-vrm.
  * **Backend:** Python 3.11 + FastAPI.
  * **NLP:** SpaCy (для токенизации) или кастомные словари.
  * **Database:** PostgreSQL (хранение связей "слово-файл").
  * **Cache:** Redis.
  * **DevOps:** Docker, Nginx.

Это ТЗ покрывает основные риски и дает четкое понимание разработчикам, как обеспечить работу виджета при высокой нагрузке.
